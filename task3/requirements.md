1. Требования к безопасности

1.1. Безопасность передачи данных (TLS)

Требование: Все взаимодействие между системами PropDevelopment (мобильное приложение, бэкенд) и внешней платформой партнера должно осуществляться исключительно по протоколу TLS 1.2 или выше.

Обоснование: Предотвращение атак «человек посередине» (MITM) и защита конфиденциальных данных в пути.

1.2. Хранение и обработка биометрии и персональных данных (ФЗ-152 / GDPR)

Требование: Необходимо обеспечить хранение биометрических шаблонов (векторы лиц) в обезличенной (хешированной или зашифрованной) форме, исключающей прямое восстановление фотографии. Номера автомобилей должны храниться с использованием необратимого хеширования (с солью) для поиска.

Требование: Обработка биометрических данных должна происходить только на территории РФ (если применимо к законодательству) с согласия субъекта (собственника/жильца), полученного через мобильное приложение PropDevelopment.

1.3. Безопасность конечных устройств

Требование: Домофоны и шлагбаумы партнера должны иметь защиту от физического взлома и несанкционированного доступа к локальной сети (например, использование отдельных VLAN).

1.4. Аудит и журналирование

Требование: Обеспечение неизменяемости логов. Все события (кто, когда и каким методом открыл дверь/шлагбаум) должны логироваться на стороне партнера и передаваться в систему PropDevelopment для возможности расследования инцидентов.

2. Протоколы аутентификации и авторизации
Для обеспечения того, что команды на открытие дверей/шлагбаумов поступают от доверенных лиц или систем, необходимо определить четкие протоколы.

2.1. Аутентификация системы (mTLS или OAuth2 Client Credentials)

Требование: Для идентификации самого сервера PropDevelopment перед платформой партнера (и наоборот) при обмене данными должен использоваться один из двух механизмов:

Mutual TLS (mTLS): Двусторонняя проверка сертификатов. Наиболее безопасный вариант для server-to-server.

OAuth2 с грантом Client Credentials: Если партнер поддерживает OAuth2. PropDevelopment получает access_token по своему client_id и client_secret для каждого запроса к API партнера.

2.2. Авторизация действий пользователей (JWT или токены доступа)

Требование: При открытии двери из приложения пользователем, мобильное приложение должно подтвердить свои права перед платформой партнера.

Сценарий: Приложение PropDevelopment отправляет запрос партнеру, содержащий:

Идентификатор пользователя.

Идентификатор двери/шлагбаума.

Подписанный JWT-токен, выпущенный бэкендом PropDevelopment, который подтверждает, что данный пользователь имеет право на доступ именно к этому объекту в данный момент времени.

2.3. Управление доступом (ACL)

Требование: Платформа партнера не должна хранить собственную базу прав доступа (RBAC) в отрыве от PropDevelopment. Партнер получает от PropDevelopment список разрешений (white list) в зашифрованном виде или проверяет права путем синхронного запроса к API PropDevelopment в момент события (см. п. 3.2).

3. Организация взаимодействия между системами
Взаимодействие должно быть асинхронным и отказоустойчивым.

3.1. Тип интеграции: REST API + Webhooks

PropDevelopment → Партнер (управление данными): REST API поверх HTTPS.

Партнер → PropDevelopment (уведомления о событиях): Webhooks.

Пример: При проходе через домофон по лицу или при въезде машины, партнер отправляет POST-запрос на заранее известный endpoint PropDevelopment с информацией о событии (успех/неудача, метка времени, фото/номер).

3.2. Сценарии проверки прав доступа

При считывании лица/номера, партнер отправляет слепок данных в PropDevelopment, и PropDevelopment возвращает ответ "Доступ разрешен/запрещен". Этот сценарий требует высокой доступности API PropDevelopment (SLA 99.9%).

3.3. Надежность и отказоустойчивость

Требование: Поддержка механизма Retry (повторов) с экспоненциальной задержкой при отправке webhooks от партнера к PropDevelopment, если endpoint PropDevelopment временно недоступен.
Требование: Очереди сообщений (Queue). При пиковых нагрузках (например, въезд 100 машин подряд в час пик) система партнера должна гарантировать доставку событий, буферизируя их на своей стороне.

3.5. Управление конфигурацией устройств

Требование: Возможность удаленной блокировки конкретного устройства (домофона/шлагбаума) через API партнера со стороны PropDevelopment в случае компрометации или неуплаты услуг собственником.
